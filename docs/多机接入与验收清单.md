# 多机接入与验收清单

目标环境为 2–4 台独立物理 NVIDIA 主机。当前控制面和单卡协议测试已可运行，机器清单和同一版本的 13B 模型权重仍需由参与者提供。不要把同一张 GPU 的多个容器或 WSL 发行版作为独立节点登记。

## 先收集只读资源报告

`edge-agent --inspect` 不启动监听端口、不创建部署、不联系控制面、不读取或输出认证令牌，也不创建 Petals 身份文件。它调用本机 `nvidia-smi` 和现有内存采集器，输出 JSON 后退出。无法采集 GPU 或内存时输出错误并以非零状态退出；不会用模拟卡或 0 MiB 补齐。

在安装了 Go 1.22+ 的主机上，从仓库根目录执行：

```powershell
go run ./cmd/edge-agent --inspect
```

也可以在管理机为 Windows x64 编译，再将生成的可执行文件通过团队已有渠道提供给参与者：

```powershell
go build -o tmp/edge-agent-inspect.exe ./cmd/edge-agent
./tmp/edge-agent-inspect.exe --inspect
```

主机报告之后，还要在**实际部署用镜像**内检查。构建当前版本的 Agent 镜像后，例如 Petals：

```powershell
docker run --rm --gpus all --network none --entrypoint /usr/local/bin/edge-agent compute-platform-petals-agent:local --inspect
```

覆盖入口可以跳过 Petals 注册流程，不需要控制令牌。RPC 镜像也可调用同一 Agent 的 `--inspect`，使用该镜像内实际 Agent 路径。保存输出时使用 UTF-8，例如 PowerShell 中 `... | Set-Content -Encoding utf8 tmp/node-a.json`，同时检查原命令退出码。

比较报告中的 GPU UUID：同一张卡在 Windows、WSL 和 Docker 中出现，仍只算一份显存。容器的可用 RAM 可能低于 Windows 主机，调度必须以 Agent 实际运行环境的预算为准。单次报告不填写需要时间差采样的 CPU 利用率；报告中的 GPU 管理数据不证明引擎支持对应 CUDA 架构。

另行记录每台主机的系统、驱动版本、可互通私网/VPN IP、所属地点和模型磁盘剩余容量。报告与这些信息留在团队内，不放入公开仓库；不要通过聊天发送密码、私钥或控制令牌。GPU UUID 能用于排除重复卡，但不能独立证明操作者声明的物理主机数量。

## 接入顺序

1. 核对所有机器独立、GPU UUID 不重复。为每台设置稳定且唯一的 `NODE_ID`；同地点可共用 `SITE`。确认显存、运行环境可用 RAM 与模型加载预算足够。
2. 在可信 LAN/VPN 配置可互通的地址。控制面和各 Agent 的共享令牌通过团队已有安全渠道配置。不要把原始 RPC 或未鉴权的 Loki 端口暴露到公网。
3. 每台使用同一固定引擎镜像版本。RPC/本机内存走 `docker-compose.distributed-agent.yml`；Petals 走 `docker-compose.petals.yml`，使用私有引导、独立持久 Peer ID。构建方式和端口见对应部署指南。
4. 各节点离线准备同一模型版本。GGUF 检查完整文件 SHA-256；Petals 每台准备完整封装目录，检查清单及各权重/tokenizer/模板文件。指定同一 tokenizer 和聊天模板，核对模型规模确实属于验收要求。
5. 启动 Agent 后先保持默认“禁用调度”。确认实际 GPU/RAM 心跳、后端能力、模型目录及监控都正常，再由操作员启用。
6. 在控制台创建显式网络组，成员为实际参与主机。对每个方向进行测量；例如两节点需 A→B 和 B→A，两组测量都成功且未过期才能部署。按真实测量设置阈值，不用降低阈值掩盖不可接受的聊天延迟。
7. 预览固定模型部署。检查连续块/层分配、每卡权重+KV+运行预算以及主机内存预留。模型加载、工作节点健康和实际端到端预热全部成功后才算 ready。
8. 将部署加入同版本模型入口；为每个主机接入日志采集器，核对工作服务的状态、真实字节、KV/GPU 观测和请求 ID。

## 验收证据

| 要求 | 必须保存的证据 | 不能作为替代的结果 |
| --- | --- | --- |
| 2–4 台独立主机协作 | 操作者确认的物理清单、各主机资源报告、唯一 GPU/Peer ID、实际部署放置 | 同 GPU 两个进程、两个容器、不同 NODE_ID |
| 13B 级模型 | 官方模型配置/参数规模、固定 revision、精度、各节点文件校验和 | 随机小模型、135M 模型 |
| 单卡无法容纳、集群能够运行 | 同一精度/上下文下的每卡预算与组内实际加载、预热、请求记录 | 仅把显存数字相加或只看计划预览 |
| 暖机 256 输入、最多 128 输出 | 实际 usage 和固定问题/模板，预热结果与至少 30 条正式记录 | 只数文本字符或 SSE 块 |
| 首输出 P95 ≤5 秒 | 从客户端请求开始到有效输出的测量，保留失败记录 | HTTP 200、role 事件、心跳注释 |
| 生成中位速度 ≥5 token/s | 实际生成 token 用量和明确时间口径；脚本提供包含排队/预填充的保守端到端速率 | 本地单层计算速度、少量小模型样本 |
| 故障安全与后续服务 | 运行中断链/停节点/取消时的请求错误、会话和资源清理、停止确认；满足容量的备用节点重新部署并完成新请求 | 旧会话 KV 自动恢复的未实现承诺 |
| 每服务监控 | 健康、流量和指标来源、请求 ID 对应日志、故障告警及解除 | 把探针流量当业务流量、把未采集当 0 |

按 [集中日志与协作推理验收](集中日志与协作推理验收.md) 执行基准。局域网 RPC、私有 Petals、量化+本机内存采用相同基础模型和问题对照，分别记录格式、精度和上下文差异。保存每次试验的 Prometheus 时间区间、错误和实际资源占用；不删除失败样本来让目标“达标”。

本项目目前没有自动恢复故障会话的 KV，也没有把多个地点所有显存无条件合并的能力。任何物理环境或性能要求未被证据证明，整体目标仍保持未验收。
