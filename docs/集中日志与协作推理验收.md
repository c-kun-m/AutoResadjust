# 集中日志与协作推理验收

## 管理端日志

`observability` profile 包含 Prometheus、Grafana、cAdvisor、Loki 和 Alloy。Alloy 固定为 `v1.20.1` 及镜像 digest；通过 Docker API 的 Compose 项目标签发现容器，约每 10 秒更新一次。只采集该项目的 stdout/stderr，不扫描其他项目或宿主机文件。

```powershell
docker compose -f deploy/compose/docker-compose.yml --profile observability up -d
```

Grafana 的 `compute-services` 看板共有 20 个面板，包括日志投递/重试/丢弃和项目日志；“日志服务”可切换控制面、Agent、基础设施。控制台服务监控也显示 Alloy 的健康和实际容器网络流量。Alloy 的 ready 只表示配置可用，实际投递要同时看写入指标和 Loki 查询结果。

Loki 使用持久卷保存数据，配置 7 天保留；清理由 compactor 异步完成。Alloy 的读取位置保存在独立卷。新安装或断线补采只接受最近 **55 分钟**，避免旧日志超过 Loki 的乱序窗口；超出记录计入 `loki_process_dropped_lines_total{reason="outside_collection_window"}`。已写入的数据仍保留 7 天。上传失败有有限重试，重试耗尽会丢弃；未启用实验 WAL，进程崩溃期间可能丢失尚未确认的内存批次，不提供恰好一次或零丢失保证。

旧版本 Loki 数据在容器内。升级前先停止该 Loki 容器，将 `/loki` 复制备份并迁移到新 `loki-data` 卷，保持 UID/GID `10001:10001` 后再重建；不要直接重建容器丢失旧数据。控制面的 `/data/control-plane.json` 也应在升级前备份。

控制面完成日志包含 `request_id/deployment_id/model/outcome/duration_ms`，不记录聊天正文。Agent 将每个工作进程输出包装为含 `node_id/deployment_id/service_id` 的 JSON；已知控制令牌、部署租约令牌被脱敏，跨写入的完整行处理后再公开。单行超过 8 KiB 则整行省略，最近片段保留 32 KiB。第三方引擎自身输出仍应按业务数据管理，避免开启打印提示词的调试选项。Docker 控制面/Agent/Alloy 日志轮换为每文件 10 MiB、最多 3 个文件。

在 Grafana Explore 选择 Loki，例如：

```logql
{job="compute-platform", service_name="edge-agent", node_id="node-a"}
{job="compute-platform", deployment_id="dep-example"}
{job="compute-platform", service_name="control-plane"} | json | request_id="返回的X-Request-ID"
```

工作进程自己的 JSON 位于外层 `message` 内，需要时再解析：

```logql
{job="compute-platform", service_name="edge-agent"} | json | line_format "{{.message}}" | json
```

请求 ID 不作为 Loki 标签，避免每次请求创建新流。原生 Windows Agent 的文件日志不由这个 Docker 采集器处理；其即时工作日志仍可通过控制台查看。

## 每台 GPU 主机的采集器

在已有 `.env.distributed-agent` 或 `.env.petals` 中增加：

```dotenv
COMPOSE_PROJECT_NAME=compute-node-a
LOKI_PUSH_URL=http://192.168.10.10:3100/loki/api/v1/push
LOG_MONITOR_BIND=192.168.10.11
```

`COMPOSE_PROJECT_NAME` 必须与实际项目名一致，每台唯一；`NODE_ID` 沿用物理节点 ID。RPC/本机内存 Agent 使用：

```powershell
docker compose --env-file deploy/compose/.env.distributed-agent -f deploy/compose/docker-compose.distributed-agent.yml -f deploy/compose/docker-compose.logs.yml --profile logs up -d
```

Petals Agent 换成 `docker-compose.petals.yml`，同时加 `--profile agent --profile logs`。引导主机使用 `--profile bootstrap --profile logs`。管理主机的 `LOKI_BIND` 需设为对应私网 IP，防火墙只放行团队采集器；当前 Loki 没有应用层鉴权，不能直接暴露到公网。Alloy 访问 Docker socket，虽然文件挂载为只读，仍具有 Docker API 访问能力，应只用于受信任管理主机。

在管理端 `prometheus.yml` 的 `job_name: alloy` 中添加远端 `192.168.10.11:12345`；在 `services.json` 添加健康目标，例如：

```json
{"id":"node-a-alloy","name":"Node A log collector","url":"http://192.168.10.11:12345/-/ready"}
```

重启 Prometheus 和控制面加载配置。远端采集器健康与投递指标可见；远端容器 NIC 流量没有接入 cAdvisor 时显示未采集。不要把 HTTP 探针字节当成实际服务流量。

12 条 Prometheus 告警包括推理停滞/失败/拥堵、工作进程失败/离线、状态落盘失败，以及采集器失联、日志重试和丢弃。`platform_service_state` 区分失败、加载中和正常停止，避免预期的停止触发工作进程故障告警。告警可在 Prometheus 中查看；尚未配置外部通知接收人。

可复现的端到端日志验证会创建两只临时容器，确认本项目的带身份日志可查、其他项目被排除，并清理测试容器。可选重启采集器验证续传：

```powershell
./scripts/verify-logs.ps1 -Project compute-platform -LokiURL http://127.0.0.1:3100 -RestartCollector
```

## 性能对照

`scripts/benchmark_inference.py` 只调用已部署的统一聊天入口，不自动部署模型，也不把同机进程当作独立算力。需要 Python 3.10+，没有额外依赖。

1. 将 `scripts/benchmark.example.json` 复制到 `tmp/benchmark.json`。填写真实模型入口、固定模型/tokenizer 版本、引擎版本、SHA-256 和精度。示例中的占位值必须替换。
2. 固定同一组文本问题，用各后端实际模板检查输入 token 数。比较时模型和 tokenizer 版本相同；GGUF 与 safetensors 的文件摘要及量化精度分别记录。配置中可有 1–3 个后端；显存不足以同时部署时分批运行相同问题。
3. 用环境变量 `CONTROL_PLANE_TOKEN` 提供现有认证，不把令牌放在 URL 或配置文件中。
4. 每个后端默认预热 2 次、正式测量 30 次，温度为 0，最大输出 128。各端点顺序交替，每次串行请求；不测高并发极限。

```powershell
python scripts/benchmark_inference.py tmp/benchmark.json --output tmp/benchmark-result.json
```

结果逐次保存，包含请求 ID、实际 prompt/生成 token 数、TTFT、总时间、失败记录。没有成功结束、真实 usage、有效内容，或只收到心跳，都不能记作完成。客户端总时限默认 130 秒；失败不会自动重试。结果不保存问题/回答正文或认证头；配置中的模型身份是操作者声明，需与平台登记、各节点实际校验结果一起审阅。

TTFT 从请求开始到第一个有效输出增量，包括排队。P95 使用 nearest-rank。吞吐采用保守的 **实际生成 token / 完整请求时间**，包含预填充、排队和网络，不能当成引擎内部纯解码速度；也不把 SSE 文本块数当 token 数。预热失败、正式请求失败、样本少于 30 或实际输入 token 不匹配时，只报告测量值，不判断目标达标。原计划的 13B、多物理机、256-token 输入仍需单独核实；脚本不会宣布多机验收完成。

完整验收还应保存每台 GPU UUID、主机身份、模型清单和链路测量；同步导出 Prometheus 的 GPU/RAM/KV、网络流量、队列、TTFT 和错误历史。比较局域网 RPC、私有 Petals、量化+本机内存时，明确不同量化方法会影响容量与输出质量。

## 故障验证

已有自动化覆盖请求排队、首 token/生成停滞/总超时、断流、取消、资源预留与停止确认。真实 GPU 冒烟分别验证进程死亡、整个进程组冻结无响应、控制租约失联；异常中的请求失败，不自动重放旧会话。

网络整形仅允许在独立、只有 `lo` 网卡的 Docker 容器内运行；脚本拒绝普通主机网络。安装 `tc` 的镜像仅用于实验，不用于生产 Agent：

```powershell
docker build -t compute-platform-petals-fault-lab:local -f deploy/compose/Dockerfile.petals-fault-lab .
docker run --rm --init --gpus all --network none --cap-add NET_ADMIN --shm-size 1g --mount type=bind,source=D:/project/resource_adjust/python/petals_backend,target=/opt/platform/petals_backend,readonly --mount type=bind,source=D:/project/resource_adjust/scripts,target=/scripts,readonly --mount type=bind,source=D:/project/resource_adjust/tmp,target=/workspace compute-platform-petals-fault-lab:local --failure-mode pause --delay-ms 100 --rate-mbps 20 --benchmark-client /scripts/benchmark_inference.py --output-dir /workspace/network-fault-results
```

替换示例中的仓库绝对路径。延迟/限速只匹配两个工作节点的 TCP 端口；结果保留 `tc` 实际处理包计数。`--loss-percent` 可注入最多 5% 丢包，未指定时为 0。实验只验证协议与退化行为；随机小模型、回环网络、单 GPU 两个进程、少量请求均不能代表真实异地容量或性能。`tc` 的时钟精度及 TCP 行为也使网络仿真与真实链路不同，见 [netem 手册](https://man7.org/linux/man-pages/man8/tc-netem.8.html)。

`agent_smoke --allocator-oom` 可以验证真实 CUDA 分配失败：只给测试工作进程分配 0.1% 的 PyTorch 显存额度，触发实际 `torch.OutOfMemoryError`，检查 Agent 报告失败、推理拒绝以及停止确认。这不需要耗尽整张显卡，不等于大模型实际峰值显存或系统内存压力验收。例如在前述隔离 Agent 容器命令中使用 `-m petals_backend.agent_smoke --allocator-oom`，并挂载当前 `python/petals_backend` 源码。

13B 的真实内存峰值、多物理机持续压测和替代节点重新部署仍需独立验收环境。不要在承载用户工作负载的 GPU 上故意耗尽显存。

配置依据：[Alloy Docker 日志](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.docker/)、[Loki 保留策略](https://grafana.com/docs/loki/latest/operations/storage/retention/)。
